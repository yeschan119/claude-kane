# kane 개발 규칙

## 0. 코드 쓰기 전 — 작업 모드 게이트
- 요청을 받으면 **바로 코드를 쓰지 않는다.** `/kane:design` 절차: ① 모드 분류(기능추가·기능수정·버그해결) → ② 조사 → ③ 설계 → ④ 승인 게이트 → ⑤ 구현 → ⑥ 검증 → ⑦ 완료 보고.
- 승인 전에는 코드 작성·파일 수정·마이그레이션·커밋·배포를 하지 않는다. 훅이 git 레포 안 코드 파일 편집을 막는다(`.md`·`.claude/`·`docs/` 제외).
- 게이트는 사용자가 연다: 승인 직후 Claude 가 게이트 명령으로 열고(사용자 확인창), 간단한 수정은 사용자가 `/kane:design on [분]`. **훅에 막힌 사실은 게이트를 열 사유가 아니다.**
- 모드가 섞인 요청은 나눠서 각각 승인받는다. 내가 덧붙인 제안은 승인 범위가 아니다.

## 1. 설계 원칙 — DRY · KISS · YAGNI
- **DRY**: 같은 로직이 두 번 필요하면 공통으로 뽑는다. 판정·산식을 두 곳에 두면 한쪽만 고쳐져 값이 갈린다. 단, 우연히 닮은 코드는 합치지 않는다 — 함께 변할 이유가 없으면 중복이 아니다.
- **KISS**: 읽는 사람이 한 번에 이해하게 짠다. 영리한 한 줄보다 지루한 세 줄. 중첩은 조기 반환·함수 분리로 편다.
- **YAGNI**: 지금 필요 없는 것은 만들지 않는다. 미리 만든 코드는 검증 없이 잠들어 있다가 터진다. 안 쓰는 코드는 지운다 — git 이 기억한다.
- 클래스는 책임 하나, 함수는 동작 하나. 비즈니스 로직과 입출력·외부 API·DB 접근을 분리한다.

## 2. 이름
- 역할이 드러나게. 함수는 동사로 시작(`createUser`), 클래스는 명사(`OrderRepository`), boolean 은 `is/has/can`.
- `qty`·`tmp`·`data`·`val`·`cnt` 같은 모호한 이름 금지 — 무엇의 값인지 드러낸다(`sold_quantity`). 이름과 실제 값이 일치해야 한다.
- 의미 있는 숫자·문자(가중치·임계값·비율·상하한)는 이름 있는 상수로 뽑고 의도·단위를 적는다.

## 3. 예외 처리
- 실패 가능한 로직(외부 API·파일·DB·네트워크)은 실패 케이스를 처리한다. 예외를 삼키지 않는다.
- 처리할 수 있는 수준에서만 잡고, 못 하면 상위로 넘긴다. 에러 메시지는 원인을 알 수 있게.
- 사용자에게 보이는 에러와 내부 디버깅용 에러를 구분한다.

## 4. 모듈·의존성
- 기능 단위로 파일을 나누고, 한 파일에 책임을 몰지 않는다. 순환 의존을 만들지 않는다.
- 의존성은 생성자·파라미터로 주입한다. 외부 라이브러리는 얇은 어댑터 뒤에 둔다. 테스트하기 어려운 전역 상태·숨은 의존성을 피한다.

## 5. 코드 작성 방식
- 기존 스타일·구조를 먼저 확인하고 따른다. 변경 범위는 요청과 직접 관련된 곳으로 제한한다.
- 불필요한 추상화를 만들지 않는다. 동작을 바꾸는 리팩터링은 이유가 명확할 때만.
- **주석·docstring 은 한 블록 2줄 이내** — 무엇을·왜만. 배경 서사·대안 비교는 커밋 메시지·PR 본문으로.
- 응답·반환값에 지금 읽는 소비자가 없는 키를 넣지 않는다.

## 6. 로그
- 실패·예외에는 원인 파악에 필요한 컨텍스트를 남긴다. 레벨을 목적에 맞게(debug·info·warn·error).
- 개인정보·토큰·비밀번호는 로그에 넣지 않는다. 같은 의미의 로그를 여러 곳에 중복하지 않는다.

## 7. 검증 · 완료 기준
- **검증을 돌리지 않았으면 "완료"라고 말하지 않는다.** 못 돌렸으면 그 사실과 이유를 적는다.
- 레포에 실제로 있는 검증 명령만 쓴다. 관련 검증이 없으면 **없다고 보고**한다 — 만들라는 뜻이 아니다.
- 정적 검사 통과 ≠ 동작 확인. 실제로 지나가지 않은 경로는 "미검증"이다.
- 구현한 컨텍스트에서 스스로 승인하지 않는다 — 검증은 `kane:verifier` 같은 별도 레인에서.
- **지시받지 않은 테스트 파일은 커밋하지 않는다.** 검증용 스크립트는 scratchpad 에서 끝낸다(훅 차단, 해제 `/kane:testfile on`).
- 기존 테스트의 단정을 고쳐야만 통과한다면 설계를 되짚을 신호다 — 고치기 전에 사용자에게 보고한다.

## 8. 위험 작업 · git
- **commit · push · PR 은 각각 명시 승인**을 받는다. "진행해/수정해"는 커밋 승인이 아니고, 확인창은 승인 절차가 아니다.
- PR 은 올릴지 먼저 묻고, base 브랜치와 담길 커밋 목록을 함께 보인다. `gh pr create` 는 `--base` 를 명시한다.
- 커밋 메시지는 사용자의 언어로 상세하게: 목적이 드러나는 제목 + 본문에 `변경 내용`·`검증`·`영향 범위`.
- 비가역 명령(강제 푸시·`reset --hard`·`clean`·`--amend`·`rm -rf`·DROP/TRUNCATE·볼륨 삭제)은 훅이 막는다. 필요하면 영향·복구 방법을 설명하고 사용자가 `/kane:danger on` 으로 연다.
- 운영 데이터 수정, 배포, 마이그레이션, 외부 발송, `.env`·시크릿·권한 변경은 승인 후에만 한다.
- 원격·운영 서버는 읽기 전용이 기본이다. 비밀번호·토큰·개인정보를 출력·커밋하지 않는다.
- 사용자의 기존 변경을 임의로 되돌리거나 덮어쓰지 않는다. 삭제·덮어쓰기 전에는 대상을 먼저 본다.

## 9. 보고
- 최종 보고에는 변경 내용 · 검증 결과(실행한 명령과 결과) · 남은 리스크를 담는다.
- 측정·코드로 확인한 것만 단정한다. 추정은 추정이라고 표기한다.
- 비교 결과는 나열하지 말고 표 + 판정 한 문장으로.
- 사용자 결정이 필요하면 선택지 2~4개로 묻는다.

## 10. 교훈 누적
- 사용자에게 지적·교정을 받으면 `/kane:learn` 으로 `.claude/lessons.md` 에 남긴다. 다음 세션 시작 때 자동으로 주입된다.
